# direct 模式失败复盘（绕道提醒）

**结论先说：direct 模式已废弃（0.2.5 / 0.2.6 已发布但代码与文档已回滚，0.2.7 恢复 0.2.4
的稳定实现）。不要再用"跳过规划器直接调 backend.einsum"当作加速手段。**

## 当初的设想

给 `qcd-einsum` 加一个"最高计算密度"开关：跳过规划器与内存重划分，方程命中专用 kernel
就用 kernel，否则一次 n 元调用 `backend.einsum`，让实际计算在时间里占比最大。接口为
`PYQCD_EINSUM_DIRECT=1` 与 `pe.configure_direct(...)`。

## 实测为什么不行

本机 `float64`/`complex128`，默认模式（规划器 + 计划缓存）为基准：

| 形态 | 默认 | direct | 代价 |
|---|---|---|---|
| 核子 2pt nvec=32（命中 Python 级专用 kernel） | 16.7 ms | 14.4 ms | 0.86×（唯一不亏） |
| 逐元素 4000² | 21.0 ms | 28.0 ms | 1.33× 慢 |
| 批量 8×256² | 3.5 ms | 25.3 ms | 7.2× 慢 |
| 矩阵乘 1024² | 18.3 ms | 199 ms | 10.9× 慢 |
| γ 夹心 512×512（注册态但**无 Python kernel**） | 6.3 ms | 187 ms | 29.9× 慢 |
| 矩阵乘 2048² | 79.6 ms | 3.48 s | 43.7× 慢 |
| 三算子链 3×256 | 0.6 ms | 2.21 s | 3900× 慢 |
| 四算子链 4×2048 | 0.27 s | 10 分钟未返回（中止） | — |

原因很简单：`numpy/cupy.einsum` 的 `optimize=False` 是**朴素 n 元循环**，不调用 BLAS、
不切分中间体，代价随算子个数指数恶化；而我们默认路径的价值恰恰来自"选顺序 + 走 BLAS"。
连两算子矩阵乘都慢 10–44×，因为默认路径会走 BLAS，direct 走的是标量循环。

## 三个具体教训

1. **"跳过规划"不是加速项，是放弃优化项。** 规划只占小/中型图 31–84% 的时间，但它换来
   的是 BLAS 与中间体控制；省下规划开销、丢掉 BLAS，净效果恒为大幅变慢。
2. **"注册态"不等于"有 kernel"。** `_specialize` 里有 9 个形态，但只有核子 2pt/3pt 主项
   有 Python 级 kernel；γ 夹心等形态是 `plan-cache`，它的 CUDA 融合 kernel 在**原生执行器
   内部**——direct 跳过执行器，于是退化成 backend.einsum，慢 30×。判断"是否命中 kernel"
   必须看实际执行分支，不能看注册表。
3. **不要用"更快"假设替代测量。** 最初只测了单算子与小形态，看起来"持平"；一旦上到
   三算子链，代价是 3 个数量级。基准必须覆盖算子数递增的形态（2 / 3 / 4 算子），
   否则会把灾难性退化当成"可能慢数倍"。

## 如果将来确实需要"低开销执行"

- 需要的是**更快的规划**（已用 opt_einsum dp + 计划缓存，见 0.2.4），不是跳过规划；
- 需要的是**更少的中间体**（批量执行、融合 kernel），不是不做中间体管理；
- 若确实只想跑一次 n 元 einsum，用 `pe.contract(..., optimize=False)`——语义明确，
  不伪装成"高性能模式"，也不会额外引入一个全局开关与其告警。
