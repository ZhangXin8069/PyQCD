### S2 — 实现（单一新模块 + 惰性导出）
- 文件: `pyqcd/parallel/einsum.py`（719 行）、`pyqcd/parallel/__init__.py`（改惰性解析）、
  `pyqcd/parallel/AGENTS.md`
- 设计要点:
  - `_normalize_tasks` 支持 dict 与 list，保持一一对应；键集合白名单校验
  - 工时 `contract_path(optimize='greedy').opt_cost`，逐元素方程以元素数兜底
  - LPT 装箱（堆实现），最慢进程 ≤ (4/3-1/(3K))×OPT
  - 进程数 `min(子任务数, CPU 线程数, 内存预算)`，`max_procs` 可收紧
  - 三条路径：serial / collective（MPI 内，零序列化）/ self-launched（自建 mpirun 池）
  - 失败即整体失败并点名任务键；`broadcast=True` 可让所有 rank 持有结果
- 关键输出: `python -c "import pyqcd.parallel"` 从 0.63 s 降到 0.007 s，且不拉入 `pyqcd.einsum`

### S3 — 实测中发现的四个真实缺陷（均已修）
1. `_package_root()` 少算一层目录 → worker `-m` 找不到包（ImportError）
2. `_slim_plan` 按 rank 数截断箱子而非重装箱 → 结果缺项 `KeyError`
3. `_threads` 把 `OMP/BLAS` 线程写进环境，worker 当作用户显式设置照搬 →
   4 进程 × 4 线程超订，collective 从 3.09× 掉到 2.28×；改为按 `物理核数//进程数` 重算
4. `mpi4py` 导入 1.6 s、`detect_resources` 为拿显存 `import torch` 1.0 s，都在热路径上 →
   worker 先查启动器环境变量、调度改用轻量 CPU/内存探测

### S4 — 真实格点 QCD 实测（`complex64`，单线程公平基准，结果与串行对照）
- collective `-np 2`：S1 Nvec=40 ×8 → 168.5 ms → 88.3 ms（1.86×）
- collective `-np 4`：183 ms → 59 ms（**3.09×**）
- 自建池 ×4：S1 Nvec=40 217→391 ms（0.56×）；Nvec=60 736→622 ms（1.18×）；
  Nvec=100 5326→2160 ms（**2.47×**）
- 结论: collective 高效；自建池固定成本约 0.2–0.3 s（mpirun 启动 + 落盘/回读 1.5 GB/s），
  串行 ≳1 s 才划算

## 推理依据

* **工时用 FLOP 而非任务数**：任务数均分会产生短板；`contract_path(optimize='greedy').opt_cost`
  是库内已有的权威代价，逐元素方程（无求和）以输入/输出元素数兜底。
* **LPT 而非贪心轮询**：给出 `4/3-1/(3K)` 最坏界，正好对应"绝不能有短板"的要求。
* **进程数默认为上限**：`min(子任务数, CPU 线程数, 内存预算)`，任务少时自动一对一。
* **两种 MPI 拓扑**：已在 `mpirun` 内时零序列化；单进程时自建池，用临时目录交换数据。
* **单精度**：dtype 完全由操作数决定，用户传 `complex64/float32` 即减半内存与算力，
  本功能不做任何类型转换（遵循"最小改动、不改变原语义"）。
