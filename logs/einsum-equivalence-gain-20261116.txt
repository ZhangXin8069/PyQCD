结论摘要（先看这四行）
--------------------------------------------------------------------------------
1. 映射的**理论上界**确实存在：语料内方程「规范写法 specialize=False ÷ 规范默认」
   中位 **1.86×（CPU）/ 1.92×（GPU）**，59/53 格里只有 6 格 < 1（GPU 侧全部是
   cuda_dedicated 本身比 generic 慢的反例）。特化路径的收益是真的。
2. 但**通过等价映射拿到这份收益，实测并不成立**：把变体映射回规范写法后，
   按库文档给的「transpose 视图」方式算，收益中位 **1.83×（CPU）/ 1.70×（GPU）**，
   却伴随 **18/59 与 15/53 格变慢**（最低 0.02×，即慢 50 倍）。
   分族看更清楚：`axes`（改单操作数轴序）族的视图口径中位只有
   **0.76×（CPU）/ 0.94×（GPU）**，14/16 与 10/14 格变慢。
   改为「先 ascontiguousarray 再算」才稳定：整体中位 1.98× / 1.91×，仅 4/59、7/53 格 < 1。
3. **映射开销是 ms 级，不是 µs 级**：对调用方真正会传的变体方程，
   `normalize_equation()` 实测中位 **39.4 ms**（CPU 与 GPU 同值，纯 Python 枚举），
   区间 23.5–60.1 ms；与 arity 强相关（arity 6 → 24 ms，arity 14 → 60 ms）。
   只有「方程本身已命中」时才 4.3–5.4 µs（warm）。主任务给出的「µs 级」预期不成立。
   **97% 的时间在 `_candidate_equations` 的候选枚举**（每次物化 3.8k–9.8k 条），
   而不是语料查表（`_specialize.match` 热态 0.4 µs）。
4. 因此**盈亏平衡点在数十到数百次同方程调用**：CPU 中位 **139 次**
   （p25 46 / p75 195 / max 1180），GPU 中位 **32 次**（p25 26 / p75 44）。
   单次或几十次的调用，映射净亏；112 个测量格子里 CPU 51/59、GPU 53/53 的
   单次执行耗时 < 5 ms，**比映射开销本身还便宜**。

**必须记录的一个测量陷阱（本报告的计算口径因此改了）**：
`contract()` 在命中/未命中之间会切换 OpenMP/BLAS **线程档**（`_threads.apply_profile`：
命中→`kernel` 档，未命中→`generic` 档）。实测一次 `kernel+generic` 往返切换
**3.8 ms（中位，30 次）**，而本库大量格子本身只有 0.1–0.9 ms。因此**严格交错
A/B/A/B 计时会把切换代价算进被测格子**，在小方程上直接失真一个数量级：
seq=1 的 c1 格，连续块测 0.100 ms，严格交错测 **2.60 ms（26×）**。
所以本报告**每格独立连续块计时**（块内档位稳定、切换只发生一次且落在 warmup 里），
并把同一格子的交错数字单列出来（§5.2），不让它污染主表。

- 语料 8638 条**全部**都能编码出 dedicated 步表（`no dedicated plan: 0/8638`），

`distill` 档单次 **13.4 s**），超出门限，未纳入主表；它的 1e8 中间体同样超门。
**因此本报告不对 `kupl_topology` 的收益下结论**，只把它作为「映射后可能落到的
另一条路线」记录其存在与代价（§4.3、§6.3）。

1.3 四组合（+1）单元格定义
--------------------------------------------------------------------------------
| 代号 | 写法 | specialize | 期望路线 |
|---|---|---|---|
| c1 | 规范（语料原文） | 默认 | 特化（dedicated） |
| c2 | 规范 | `False` | 通用（= 映射的价值上界） |
| c3 | 变体 | 默认 | 通用（未命中） |
| c4v | 变体经映射回规范，操作数按 `operand_permutations` 做 **transpose 视图**（库文档的原话是「张量需 transpose…」） | 默认 | 期望特化 |
| c4c | 同 c4v，但先 `ascontiguousarray` 落一份连续副本 | 默认 | 期望特化 |

c4 有两个版本是必要的：库文档只说「transpose」，没说清视图还是副本，而这两种在
本库里**走的是完全不同的路线**（§4）。

两个收益定义：
- **映射收益** = c3 ÷ c4（变体直接算 vs 映射后算）。这是「用这个功能到底值不值」；
- **理论上界** = c2 ÷ c1（规范 specialize=false vs 规范默认）。这是「特化本身值多少」。

1.4 等价变体的构造与等价性验证
--------------------------------------------------------------------------------
每样本构造 2–4 个变体，逐条过等价性门（`rtol=1e-12`，按输出 `max|·|` 归一）：

| 族 | 构造 | 需要的映射 |
|---|---|---|
| `order` (swap01 / swap23) | 交换两个操作数位置，张量按新次序传 | `operand_order` |
| `axes{i}` | 把第 i 个操作数（全轴 >1、秩≥2、无重复标签）的轴序整体反转，张量物理存成变体的轴序 | `operand_permutations` |
| `outrev` | 输出段轴序反转 | `output_permutation`（结果需 reverse-transpose 回比对） |

数值门结果：**全部纳入的变体 `rel ≤ 1.1e-15`**（`rel_variant_vs_canonical`，
输出轴族在按 `output_permutation` 转回之后；`rel_mapped_vs_canonical` 全部 ≤ 6.4e-16）。
另有 1 个变体在首轮被这条门**拦下并丢弃**：seq=855 的 `outrev` 初版比对时未做
逆置换，`rel=1.13` —— 这正是「必须验证等价性」要防的错误，修正逆置换方向后
`rel=0.0`，才重新纳入。

**组合改写不被支持（实测）**：`swap + axes` 或 `swap + output` 这类同时改两族的写法，
`normalize_equation` 返回 `None`，`explain` 给 `rewritten=False`：

```
seq 855  "hdgc,nbma,eifj,...->ak"  (swap 0/1 且两操作数轴序反转)
  _specialize.match -> None
  _equivalence.explain -> rewritten=False, reason=没有任何等价写法能……
```

原因在实现里很清楚：`_candidate_equations` 的 ①操作数位置 / ②单操作数轴序 /
③输出段轴序是三段**并列枚举**，每段都是在**原文**上改一处，没有做两段叠加。
因此「只改了一处的写法」才可能被映射；这也是「映射了但没变快」之外的一个
**功能边界**（不是性能问题，但直接决定这个功能覆盖多少真实场景）。

三、映射收益 vs 理论上界
--------------------------------------------------------------------------------

3.1 汇总（全部家族）
--------------------------------------------------------------------------------
| 指标 | CPU n=59 | GPU n=53 |
|---|---|---|
| 映射收益（c3/c4v，transpose 视图） | min 0.02 / p25 0.83 / **中位 1.83** / max 8.17；**<1 共 18** | min 0.07 / p25 0.97 / **中位 1.70** / max 4.60；**<1 共 15** |
| 映射收益（c3/c4c，连续副本） | min 0.02 / p25 1.62 / **中位 1.98** / max 8.26；**<1 共 4** | min 0.13 / p25 1.60 / **中位 1.91** / max 4.17；**<1 共 7** |

读法：
- CPU 上理论上界**从不小于 1**（0/59 变慢），说明「映射能带来的最好结果」恒为正；
  映射后的实际收益在「连续副本」口径下与上界基本重合（1.98 vs 1.86，甚至略高，
  因为 c4c 与 c1 走同一条可执行路径但方程文本不同，计划缓存/线程档状态略有差异）。
- GPU 的上界有 6 格 < 1，全部来自 seq 2583 / 3436：这是**特化本身在 GPU 上比通用慢**
  的已知反例（见 §6.2），映射救不了它，反而会把变体的通用路径换成更慢的特化路径。
- 「transpose 视图」口径下的收益**不稳定**：CPU 18/59、GPU 15/53 变慢。这不是
  噪声，是路线差异（§4.3），必须单列。

3.2 收益 < 1（变慢）的行清单

**CPU，gainV < 1**（全部 18 格）：seq 1/2/3/849/855/1599/1606/1623/1743/1863/866/2583/2584/3436

四、为什么「映射了却没变快」——三个可复现的机制
--------------------------------------------------------------------------------

4.1 机制一：专门路径要求 C 连续，transpose 视图天然不连续
--------------------------------------------------------------------------------
`_kernel_kupl.try_dedicated` / `_kernel_cuda.try_dedicated` 的第一道门就是：
```
if any(not operand.flags["C_CONTIGUOUS"] for operand in operands):
    return _fail("dedicated kernel requires C-contiguous operands")
```
而 `_equivalence` 的 `operand_permutations` 文档原话是「张量需 `transpose(perm)`」。
`transpose()` 返回的是**视图**，除恒等/两两交换以外都不连续。于是：

| 口径 | seq 855 的路线 | 说明 |
|---|---|---|
| c4v（视图） | **kupl_topology** | dedicated 因不连续被拒，落到路由链的下一站 |
| c4c（副本） | kupl_dedicated | `ascontiguousarray` 之后命中 |

**结论：库文档给的用法（直接 transpose）会稳定地绕过 dedicated。** 这是本报告
所有 `gainV < gainC` 的根因，且这不是「变体没映射成功」，而是「映射成功后按文档
用，走的路和规范写法不一样」。

4.2 机制二：`kupl_topology` 在 CPU 上常常比通用还慢
--------------------------------------------------------------------------------
视图落到 topology 后的代价（CPU，同一 `axes` 族，c4v vs c4c）：

|---:|---|---|---:|---:|---:|
| 1 | `ac` | kupl_topology | 0.345 | 0.113 | 3.1× 慢 |
| 2 | `ac` | kupl_topology | 0.381 | 0.117 | 3.3× 慢 |
| **3** | **`egfh`** | **kupl_topology** | **117.776** | **1.570** | **75.0× 慢** |
| 849 | `ac` | kupl_topology | 0.465 | 0.112 | 4.1× 慢 |
| 855 | `ce` | kupl_topology | 0.719 | 0.327 | 2.2× 慢 |
| 1599 | `ac` | kupl_topology | 0.509 | 0.123 | 4.1× 慢 |
| 1606 | `ac` | kupl_topology | 0.628 | 0.145 | 4.3× 慢 |
| 1623 | `ce` | kupl_topology | 0.908 | 0.342 | 2.7× 慢 |
| 1743 | `ac` | kupl_topology | 0.844 | 0.375 | 2.3× 慢 |
| 1863 | `ac` | kupl_topology | 1.163 | 0.382 | 3.0× 慢 |
| 2583 | `cadb` | kupl_topology | 1.222 | 0.249 | 4.9× 慢 |

**16/16 个视图格都落到 topology，其中 14/16 比 dedicated 慢**（中位约 2.6×，
最坏 75×）。这与库里已经记录的口径一致：`kupl_topology` 在小/中规模上有约
1–2 ms 固定入口开销，而这里的大多数格子本体只有 0.1–0.9 ms。

4.3 机制三：GPU 上视图连 topology 都进不去
--------------------------------------------------------------------------------
GPU 侧 `cuda_topology` 对非连续输入的处理与 CPU 不同，实测 `axes4`(seq 855)：

```
direct try_dedicated       -> MISS  "dedicated kernel requires C-contiguous operands"
direct try_topology_apply  -> MISS  (159.08 ms)  "NativeUnavailable: qcd_cuda_topology_apply …"
contract(...) × 20         -> routes = {'generic': 20}
   median 3.506 ms  vs  contiguous copy 2.378 ms
```
即：视图在 GPU 上**既没有 dedicated、也没有 topology**，直接掉到通用路径，
而这条通用路径还要付 159 ms 的拓扑尝试失败代价（一次性，之后命中负缓存）。
同一格在 GPU 主表里表现为 52.022 ms（首轮被计入中位），是本次测量中最严重的单点。

五、映射开销与盈亏平衡
--------------------------------------------------------------------------------

5.1 开销本体（**这是主任务预期之外的结果**）
--------------------------------------------------------------------------------
主任务的预期是「μs 级」。实测不是。分两种情形，差三个数量级：

| 调用对象 | `normalize_equation` (中位) | `explain` (中位) | 说明 |
|---|---:|---:|---|
| 方程**本身已命中**语料（例如规范写法） | **4.3–5.4 µs** | 6.3–8.1 µs | `probe(equation)` 第一次就 True，直接返回 `kind="identity"` |
| 方程**需要改写**（变体，即真实用途） | **23.5–60.1 ms**（中位 39.4 ms） | 23.7–60.0 ms | 全量枚举候选并逐个 probe |

按 arity 分（warm cache，9 次中位）：

| arity | n | `normalize_equation` ms | 候选数 `find_equivalents` |
|---:|---:|---:|---:|
| 6 | 4 | 23.5 – 25.4 | 3815 – 4002 |
| 7 | 1 | 30.1 | 4867 |
| 9 | 2 | 36.6 – 39.1 | 5799 – 6187 |
| 10 | 2 | 39.2 – 40.8 | 6198 |
| 12 | 2 | 40.1 – 41.5 | 6106 |
| 13 | 2 | 42.4 – 44.3 | 6269 |
| 14 | 2 | 58.3 – 60.1 | 9826 |
| 16 | 1 | 45.7 – 46.8 | 6433 |

拆解（arity 16，seq 1863，axis 变体）：
```
_candidate_equations(...)        46 444 µs   (6433 个候选)
_specialize.match (热)                0.4 µs   × 6433 ≈ 2.6 ms
normalize_equation(同式)         47 369 µs
explain(同式)                    47 042 µs
```
**97% 的时间在 `_candidate_equations` 的纯 Python 枚举与字符串拼接上**，不在语料查表。
`_specialize.match` 本身是正确的 0.4 µs（语料索引已缓存），不是瓶颈。

一个反直觉点：**「命中得早就便宜」在这里不成立**。`normalize_equation` 是
「按候选顺序逐条 probe，第一条通过就返回」，理论上 swap 变体应该在很靠前的位置
就命中；实测其耗时与「枚举到底仍然失败」几乎相同（seq 855：40.0 ms vs 40.8 ms；
seq 1863：46.7 ms vs 46.9 ms）。原因是 `_candidate_equations` **先把全部候选
物化成 list**，之后才进入 probe 循环——「提前返回」只省掉了 probe，没省掉枚举。

5.2 交错计时的额外代价（必须单列，不能算进被测格子）
--------------------------------------------------------------------------------
| 项目 | 值 |
|---|---|
| `_threads.apply("kernel")` + `apply("generic")` 一次往返 | **3.8 ms**（CPU 中位）/ 5.8 ms（GPU 进程内实测） |
| seq 1 c1 格：连续块 0.100 ms → 严格交错 **2.601 ms** | 26× 失真 |
| seq 1 c2 格：连续块 0.183 ms → 严格交错 0.207 ms | 基本不变（generic 档不切换） |

即：**任何把「命中」与「未命中」严格交错的计时，在小方程上测的是线程档切换**。
本报告因此用连续块（§1.1），并把这一条写成显式警告，供后续基准复用。

5.3 盈亏平衡
--------------------------------------------------------------------------------
盈亏平衡调用数 = 映射开销 ÷ 每次执行省下的时间（c3 − c4）：

**CPU（`order` 族，c4c 口径）**
| seq | arity | 映射 ms | 每次省 ms | 盈亏平衡调用数 |
|---:|---:|---:|---:|---:|
| 1 | 6 | 24.5 | 0.081 | 305 |
| 2 | 6 | 24.5 | 0.119–0.170 | 144–207 |
| 849 | 9 | 37.9 | 0.114–0.126 | 302–332 |
| 855 | 10 | 39.4 | 0.199–0.202 | 195–198 |
| 866 | 10 | 39.4 | 0.259–0.289 | 136–152 |
| 1599 | 12 | 40.8 | 0.137–0.175 | 233–299 |
| 1606 | 12 | 40.8 | 0.292–0.563 | 73–140 |
| 1623 | 13 | 43.3 | 0.311–0.351 | 123–139 |
| 1743 | 13 | 43.3 | 0.319–0.351 | 124–136 |
| 1863 | 16 | 45.7 | 0.419–0.441 | 104–109 |
| 2583 | 6 | 24.5 | 1.164–1.188 | **21** |
| 2584 | 6 | 24.5 | 0.140 / 0.529 | 175 / 46 |

**GPU（同族，c4c）**：平衡点分布 n=46，**min 13.9 / p25 25.5 / 中位 31.9 / p75 44.1 /

三条结论：
1. **单次/少量调用一定亏**：开销 23.5–60.1 ms，大于绝大多数格子的整次执行时间。
   实测 112 个测量格子里，**CPU 51/59、GPU 53/53 的规范路径单次耗时 < 5 ms**，
   也就是说映射开销比被测调用本身还贵。
2. **只有「同一条方程被调用上百次」才划算**（CPU 盈亏平衡中位 139 次、GPU 32 次）。
   而「同一条方程调用上百次」恰恰是最该直接用规范写法、根本不需要映射的场景。
3. **唯一「一次就回本」的规模是 arity 14 的 828/833 类**（每次省 370+ ms）：
   那里 c3 的通用路径要 445–455 ms，c4c 只要 58–65 ms。但即便如此，
   **映射耗时 60 ms 也只是把 450 ms 变成 60+60=120 ms**，收益从 7.6× 降到 3.8×。
   这是全表唯一把平衡点压到 0.2 次的情形，样本只有 2 条，不宜外推。

六、CPU vs GPU 差异
--------------------------------------------------------------------------------

6.1 一致的部分
--------------------------------------------------------------------------------
- **特化路径的收益方向一致**：上界中位 CPU 1.86× / GPU 1.92×，量级相同；
- **映射开销完全一致**：23.5–60.1 ms，因为它是**纯 Python 枚举**、与设备无关
  （`_candidate_equations` 不做任何数组运算）；
- **`axes` 族在两边都最容易变慢**：CPU 中位 gainV 0.76、GPU 中位 0.94。

6.2 不一致的部分（历史经验「两者可能相反」在这里得到确认）
--------------------------------------------------------------------------------
| 现象 | CPU | GPU |
|---|---|---|
| 特化 vs 通用（上界） | 0/59 变慢；最差 1.08× | **6/53 变慢**，最差 0.40× |
| 低收益反例 | seq 2584/3436（1.11–1.34×） | **seq 2583（0.40–0.44×）**、seq 3436（0.72–0.82×）——特化比通用慢 2.3–2.5× |
| 视图落到哪 | `kupl_topology`（16/16） | 6 格 `cuda_topology`、**8 格直接 generic** |
| 视图最坏格 | seq 3 `axes2` 117.8 ms vs 1.57 ms（75×） | seq 855 `axes4` 52.0 ms vs 1.25 ms（41×） |

**GPU 上特化反而更慢的反例（seq 2583）复核**（独立于 harness，20 次连续调用）：
```
canon/default      = 3.470 ms (cuda_dedicated)   | 20 连跑 min 3.012 median 3.103
specialize=False   = 1.188 ms (generic)          | 20 连跑 min 1.097 median 1.193
```
稳定复现，不是噪声。seq 3436 同向但幅度小（2.838 vs 2.183，0.77×）。
这类反例说明：**「映射回规范形式就能变快」这条前提本身不是普适的**——
在 GPU 的某些格子上，规范形式反而是慢的那一侧。

6.3 未覆盖（诚实标注）
--------------------------------------------------------------------------------
- **`kupl_topology` 作为 c1 主路线的收益完全未测**：distill 档里能走到它的 3100 条
  任务，最小中间体**恰好 1e8**，全部超门（§1.2）。唯一实测样本 seq 2585 单次 13.4 s。
  因此「CPU 上 topology 承接的样本，映射收益是多少」在本报告里是 **unverified**。
- **`cuda_topology` 作为 c1 主路线的收益也未测**：`cuda_topology` 只为 arena 超
  3 GiB 的 3308 条任务承接，其最小 maxint 是 6.4e7（在门内），但实测 seq 4427
  单次 native 295.6 ms、generic 26.5 ms（**特化慢 11×**），且它不进主表样本集
  （不属于 16 条入选样本）。这条路线的收益需要单独一轮测量。
- **float32/float64/complex64 未测**：本报告全程 complex128。
- **单机测量、CPU 是 18 核共享机**（`nproc=18`，未独占，同机另有作业）。噪声已实测：
  同一格（seq 3 规范路径）15 次连续调用为
  `[51.4, 2.63, 2.44, 2.36, 2.70, 2.60, 2.31, 2.57, 2.26, 2.29, 2.29, 2.69, 2.34, 2.43, 2.35] ms`
  —— 中位 2.43 ms，但有**一次 51.4 ms 的离群**（21×）。因此：
  (a) 主表用 9 次中位已能压掉单个离群；
  (b) §2.1 中 seq 3 首行的 c1=10.880 ms / c2=10.880 ms 那一对**应视为离群污染**，
      同格三次独立重测的 c1 分别是 1.755 / 1.74 / 2.43 ms；
  (c) 所有「接近 1」的比值（例如 2584 的 0.99–1.04）都在该噪声量级内，
      **不应据此判定「快」或「慢」**，只能判定「持平」。跨机复现需要独占环境。

---

七、结论：这个功能值不值得用，在什么规模下值得
--------------------------------------------------------------------------------

7.1 一句话
--------------------------------------------------------------------------------
**「映射本身能带来收益」是真的（上界中位约 1.9×，CPU 上 0 例外）；但「用如今这个
接口去拿这份收益」在多数格子上拿不到，甚至倒亏——因为 (a) 文档建议的 transpose
视图会绕过 dedicated，(b) 映射开销是 ms 级而不是 µs 级。**

7.2 分场景结论
--------------------------------------------------------------------------------
| 场景 | 结论 | 依据 |
|---|---|---|
| 只想问「有没有等价写法」（诊断/一次性） | **值得**，但要知道它会花 24–60 ms | §5.1 |
| 一条方程要跑 **≤ 20 次** | **不值得**：开销 23.5–60.1 ms 大于几乎全部省下的时间 | §5.3 |
| 一条方程要跑 **100+ 次**（算术密集） | **可能值得**，且必须 **先 ascontiguousarray** | §5.3 |
| arity 14 / 每次省 370+ ms 的重路径 | **一次就回本**，是唯一明确的赢面 | §5.3 |
| GPU 上 seq 2583/3436 这类「特化本身更慢」的形态 | **不该用**：映射会把通用换成更慢的特化 | §6.2 |
| 需要「交换操作数 + 改轴序」组合改写 | **不可用**：`_equivalence` 不支持组合 | §1.4 |

7.3 如果要把这个功能变得值得用（按收益/代价排序，本次均未实施）
--------------------------------------------------------------------------------
1. **文档必须写明 `ascontiguousarray`**（零代码改动，直接消掉 14/16 的视图倒亏
   与最坏的 75×）。当前文档只说「张量需 transpose」，按字面用就是最差路径。
2. **`_candidate_equations` 改成惰性生成器 + 提前返回**（约 1 行 `yield` 改造）：
   现在 97% 的时间花在把 3.8k–9.8k 个候选全部物化，而 probe 循环只用前若干个。
   按实测，swap/axes 这类变体命中位置靠前，改惰性后开销大概率从 40 ms 降到
   亚毫秒级——这才是让「µs 级」预期成立的关键。
3. **视图输入应当显式判负并说明**：`try_dedicated` 的失败原因已经写得很清楚
   （`dedicated kernel requires C-contiguous operands`），但 `try_topology_apply`
   会在 CPU 上默默地接住（常常更慢）、在 GPU 上失败后掉到 generic。
   把「不连续 → 复制或拒绝」做成显式策略，比让路由链自己漂移更可预测。
4. **不要跨设备复用结论**：GPU 的 seq 2583 上特化比通用慢 2.5×，映射的方向在那里
   是反的。

7.4 本报告不支持的结论（避免误读）
--------------------------------------------------------------------------------
- **不支持**「映射能提速 1.9×」作为功能结论。1.9× 是**特化路径的收益上界**；
  通过当前 `_equivalence` 接口把它兑现，实测视图口径有 30% 格子倒亏。
- **不支持**「映射开销可忽略」。54 µs/次 的说法只对「方程已命中」成立，
  而那正是**不需要映射**的情形。
- **不支持**「CPU 与 GPU 一致」。它们在「特化是否更慢」这一点上结论相反。
- **不支持**把本报告的 `kupl_topology` 视图数字当成 topology 的性能结论：
  那些格子的规范路线是 `kupl_dedicated`，topology 只是视图的中途落脚点。
