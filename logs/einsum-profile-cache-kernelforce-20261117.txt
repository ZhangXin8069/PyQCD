### 2. 加缓存会打破「内层命中」型契约
- 结论: 旧的 `test_full_corpus_match_cache` 断言第二次全语料扫描时内层

### 3. 去重键不能按文案
- 结论: `_warn_native_fallback_once` 早期按整条 message 去重时，同一 `status 7`
  会被编译层（"compile failed with status 7"）与执行层（"execution failed with
  status 7"）各报一次；后来改成按根因签名去重：优先用显式 `reason`，否则把
  `status N` 归一成 `native-status-N`，再否则取 `NativeUnavailable: ...` 的稳定
  文本，最后才退回整条文案。这样同一根因只报一次，不同根因各报一次。
- 证据: `pyqcd/einsum/_api.py:1411-1428`（`_fallback_signature`，其中
  `:1423` 为 `status` 正则、`:1425-1427` 为 `NativeUnavailable` 正则）、
  `:53`（`_NATIVE_WARNED_REASONS`）、`:1439-1442`（查集/入集后再 warn）；
  commit `3138ecd0` 的提交消息明确记录「native_install_diagnostics 是"按文案去重"
  导致同一 status 7 报两次——已改为按 status 归一，复跑转绿」；
  契约 `pyqcd/testing/_einsum_fallback_visibility_contract.py:31-46` 钉住
  「同 reason 去重、不同 reason 各一次」。
- 核实状态: verified（根因签名与契约可读；原始重复告警已修复，不能在本机重现，
  事件本身以 0.4.5 提交消息为准）。
- 可复用判据: 告警/日志去重先归一到稳定根因（状态码 → 异常类型/稳定文本 →
  整条消息），并同时保留「不同根因不得被吞」的契约。

### 5. 版本号与在跑的测试有竞态
- 结论: `release_metadata` 契约会在运行时重新读 `pyproject.toml`，再与进程内
  `pyqcd.__version__`、`pyqcd.einsum._version.__version__` 比对。若测试进程已经
  import 了旧版本，随后三处版本号被升到新值，磁盘上的 `pyproject.toml` 已是新值、
  进程内常量仍是旧值，于是报假失败；重跑（新进程）即过。升版本要先把三处都改完，
  再启动/重跑测试，不能边升边跑。
- 证据: `pyqcd/testing/_release_metadata_contract.py:32-39`
  （`_pyproject()` 每次读盘，`pyqcd.__version__` 是 import 期常量）；
  三处版本位点 `pyproject.toml:11`、`pyqcd/__init__.py:53`、
  `pyqcd/einsum/_version.py:3`（当前均为 `0.4.5`）；
  commit `3138ecd0` 的提交消息明确记录「release_metadata 是升版本与在跑测试的
  竞态（重跑即过）」。
- 核实状态: verified（代码机制可读；事件以 0.4.5 提交消息为准）。
- 可复用判据: 版本三处同步 → 重启测试进程 → 再跑 `release_metadata`；不要把
  「升版后旧进程里的版本不一致」当成打包/元数据回归。

### 7. 强制内核必须旁路负缓存
- 结论: 「强制」的语义是「真试一次」，但自动分派的负缓存会把确定性拒绝记下来，
  第二次直接以 `negative-cache hit: ... status 4` 挡住。正确做法是在每个 attempt
  前套内核模块自己的 `bypass_negative_cache()`：模块内计数器（0 = 不旁路，可嵌套），
  进入/退出配平，**不改 `os.environ`**（环境变量是调用方与并发线程共享的状态），
  旁路期间既不读也不写负缓存。CUDA 侧没有自己的负缓存，直接转出 KUPL 侧同名
  上下文管理器，避免造第二套机制。
- 证据: `pyqcd/einsum/_kernel_kupl.py:88`（`bypass_negative_cache`，注释从
  `:80` 起说明计数器/嵌套/不改 env）、`:112`（旁路先于环境变量判定）、
  `:165`（旁路期间不写负缓存）；`pyqcd/einsum/_api.py:659,664`（每个 attempt
  前 `bypass = getattr(...)` / `with bypass():`）；
  `pyqcd/einsum/_kernel_cuda.py:43-61`（转出 KUPL 的上下文管理器）；
  契约 `pyqcd/testing/_einsum_kernel_force_contract.py:370+`
  （连续两次强制都不许出现 `negative-cache hit`）。
- 核实状态: verified（实现与契约可读）。
- 可复用判据: 「强制」类开关要把旁路放在 attempt 边界，用模块内可嵌套计数器，
  不靠改环境变量；旁路期间既不读也不写缓存，退出后缓存计数逐项不变。

### 8. `as_equivalence` 的成本是形状相关的
- 结论: 文档示例方程 `menf,cadb,ac,em,bd,fn->`（dim=2）实测 `true` 3.281 ms /
  `false` 0.249 ms（≈13×），复现了文档记录的 2.92 ms / 0.28 ms（≈10×）量级；
  dim=8 为 2.880 / 0.270 ms（≈10.7×），dim=16 为 3.835 / 0.594 ms（≈6.5×）。
  这说明成本是一笔约 2.6–2.9 ms 的近固定开销：小形状下它占主导，形状变大后被
  计算量摊薄，所以「大批量小收缩应关闭、大方程可相对忽略」的判据成立。
- 关键限定（与文档的因果归因不同）: 这笔开销在 `--kernel generic` 下仍然存在
  （`--equivalence false` 时 true 2.948 ms / false 0.245 ms），因此它不是原生
  `kupl_dedicated` 内核本身；dim=2 只有 48 个元素，也不支持「副本带宽主导」的
  解释。具体落在映射查询、匹配查询还是递归 contract 的哪一步，本次没有逐函数
  拆解，标 unverified。
- 证据: `docs/einsum_user_guide_20261116.md:1596`（2.92/0.28 原文）；
  本次命令与输出见「## 验证与证据」的 E8 组；统一条件为本机 CPU、numpy、
  `--rounds 2 --warmup 1`、`--equivalence false`（除首条按文档默认外）。
- 核实状态: verified（量级与「形状相关」判据）；**unverified**（把开销归因于
  「改写与副本」的机制说明）。
- 可复用判据: 小形状、高频重复的批处理关闭 `as_equivalence`；判断「大方程可忽略」
  时看固定开销与计算量的比值，不要只看绝对毫秒，也不要在没有逐函数拆解时把成本
  归因于张量副本。

### H. `as_equivalence` 成本（第 8 条）
统一条件：本机 CPU、numpy、`--rounds 2 --warmup 1`；方程
`menf,cadb,ac,em,bd,fn->`，输出标量；文档示例块用默认 equivalence 报告，其余块
均加 `--equivalence false`。
```bash
# 文档示例（dim=2），默认 equivalence 报告
python -m pyqcd.einsum.test --equation "menf,cadb,ac,em,bd,fn->" \
  --shape "[2,2,2,2],[2,2,2,2],[2,2],[2,2],[2,2],[2,2]->" \
  --rounds 2 --warmup 1 --as-equivalence false
# PASS ... 0.249ms

python -m pyqcd.einsum.test --equation "menf,cadb,ac,em,bd,fn->" \
  --shape "[2,2,2,2],[2,2,2,2],[2,2],[2,2],[2,2],[2,2]->" \
  --rounds 2 --warmup 1 --as-equivalence true
# PASS ... 3.281ms（route: 特化 · kupl_dedicated）

# 隔离原生内核：强制 generic，并关掉 equivalence 报告
python -m pyqcd.einsum.test --kernel generic --equivalence false \
  --equation "menf,cadb,ac,em,bd,fn->" \
  --shape "[2,2,2,2],[2,2,2,2],[2,2],[2,2],[2,2],[2,2]->" \
  --rounds 2 --warmup 1 --as-equivalence false
# PASS ... 0.245ms
python -m pyqcd.einsum.test --kernel generic --equivalence false \
  --equation "menf,cadb,ac,em,bd,fn->" \
  --shape "[2,2,2,2],[2,2,2,2],[2,2],[2,2],[2,2],[2,2]->" \
  --rounds 2 --warmup 1 --as-equivalence true
# PASS ... 2.948ms

# 形状放大：dim=8 / dim=16（同方程，把形状里的 2 换成 8/16，其余参数不变）
# dim=8 : false 0.270ms / true 2.880ms
# dim=16: false 0.594ms / true 3.835ms
```
结论：约 2.6–2.9 ms 的近固定开销；小形状约 10×，dim=16 已降到约 6.5×。开销在
`--kernel generic` 下仍在，故不是原生内核本身；副本带宽无法解释 48 元素上的
2.6 ms，具体内部归因未拆解（unverified）。
