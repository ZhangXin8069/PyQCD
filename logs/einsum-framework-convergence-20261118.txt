## 01 · 死代码判据：`e4_fused` / `sandwich` 曾被误判

`[转述 DCA.report.md §0]` 任务背景声称两核在 `optimize="greedy"` 下"结构不可达"。
实测推翻：

```
GREEDY FIRST: (3, 6, 3, 6) [('compile',), ('native', 'ab,...bce,cd->...dae', True)]
[fused-skip] fused paths disabled (set PYQCD_CUDA_FUSED=1 to enable)   # 默认
[fused-hit] prepared                                                   # 默认（另一条门）
[fused-hit] sandwich                                                   # PYQCD_CUDA_FUSED=1
```

判定：**活代码**（入口可达，只是藏在环境门后面）。
另发现**源码与产物不一致**：包内 `.so` 比 `apply_contract.cu` 旧 5 分钟，且含源码里
根本不存在的 `PYQCD_CUDA_FUSED` 字符串。

教训：结构不可达 = 入口本身不存在；不是"入口藏在环境变量后面"。
源码/产物不匹配时，任何"产物里有哪些分支"的结论都不可靠。


只是变慢"的候选，一律按活代码处理。

## 05 · 三态语义：`forced_labels(None) == ()`

复跑（`mamba run -n pyqcd-test`）：

```
forced_labels(None) = ()
resolve(None)       = ('generic',)
parse("auto")            -> ValueError
parse("dedicated,generic") -> ValueError
tuple("dedicated")       = ('d', 'e', 'd', 'i', 'c', 'a', 't', 'e', 'd')
```

后果链（`[转述 A1/A2/SPEC6]`）：
`_api._profile_begin` 用 `caller_force is not None` 判"用户是否显式给过"，而
`forced_labels` 永不返回 `None` → **默认调用被判成"显式 generic"** →
① 命中行只要 `kernel≠generic` 就抛 `ProfileConflict`；
② `info["force"]` 永不赋值 → 画像 `force` 槽与 `_profile_retry` 整段不可达；
③ `generic_only` 恒 `True` → `as_equivalence=True` 静默失效。

修法（现落点 `_api.py:1805`）：

```python
caller_force_given = kernel_force is not None   # 显式布尔位，在解析之前取
forced = _kernel_force.forced_labels(kernel_force)
```

教训：**区分"用户真的给过"必须用显式布尔位**，不能拿解析结果反推——
`tuple("dedicated")` 那行说明"逼调用方自己包元组"也会静默变成单字符序列。

### 同族缺陷：`(requested,)` 多包一层

`KernelUnavailableError.requested` 按"序列"设计时，调用点照抄 `(requested,)` 多包一层，
`", ".join(self.requested)` 拿到元组的元组：

```
TypeError: sequence item 0: expected str instance, tuple found
    File "pyqcd/einsum/_kernel_force.py", line 134, in __init__
        label = ", ".join(self.requested) or "(none)"
```

一条 `TypeError` 连带 5 项契约连锁失败。现在的收口是
`self.requested = (requested,) if isinstance(requested, str) else tuple(requested)`：
**字符串入参自动包成 1 元组，调用方不必自己包**。

教训：`", ".join(x)` 前先确认 `x` 的层级（本轮以"入参归一"根治，而不是四处加断言）。

## 06 · 字符串开关：`bool("false") == True`

复跑：

```
bool("false")                    = True
_profile_cache.enabled("false")  = True     <-- 与直觉相反
_profile_cache.enabled(False)    = False
_kernel_force.parse("false")     -> generic  （已显式解析，正确）
```

教训：字符串开关必须显式解析，否则一处字符串就能反转行为。

## 09 · `kupl_topology` vs `kupl_topology_v2`（路线 ≠ 内核）

`[转述 CUDA_MIG / _kernel_kupl.py:712-725]` 两条路线**返回值相同、数值都正确**，
只有性能含义不同。判据是原生 `run_specialized` 的 5 道门（`topology_apply.cpp:228`）：

1. `dtype` 在四类平权契约内（且复数还要 `complex_complete()`）；
2. `cblas` 符号齐全（缺 `cgemm/zgemm` 只回落复数档）；
3. 规范化签名一致（`build_canonical_signature` + `topo_find` 命中且签名逐字相等）；
4. **编译步表命中**（`record->version == 3`，且 arity / out_rank / sizes 匹配）；
5. 秩/尺寸匹配（轴长来自 `execution.sizes`，不再要求等长轴）。

`2582/2583` 只是历史基准的观察值（基础表 2582 条 → 扩表 8638 条的分界），
**不是判据**。旧实现无条件写 `path='kupl_topology'`，导致 2026-11-15 的 77 格里
52 格实际跑 v2 却被当成 v3 的性能结论。

教训：路线必须由原生自证（`qcd_kupl_topology_last_specialized()`），不可由"返回码 0"
推断；缺该符号就 fail closed。

## 10 · `optimize="auto"` 同名不同义

| 内核 | `auto` 的真实算法 |
|---|---|
| `generic`（`_plan_py.py:769-791`） | 按算子数查 `_AUTO_CHOICES`（1–4→optimal / 5–6→branch-all / 7–8→branch-2 / 9–14→branch-1 / ≥15→greedy）；≤8 算子再用 opt_einsum DP 交叉校验 |
| `dedicated`（`_kernel_kupl.py:1471-1491` + `_effective_dedicated_optimizer:122`） | 在 `auto` 与 `greedy` 两条计划里按步表 FLOPs 取小（并列取 auto）；仅 CPU complex128 且基础 plan arena > 8 GiB、branch-2 同时把 FLOPs 压到 ≤80%、arena/pack ≤65% 时条件提升 branch-2 |

另有 `PYQCD_EINSUM_DEDICATED_PLAN` 只在调用方保留缺省时才覆盖（`optimize != "auto"`
一律不覆盖）。

教训：同一个名字在两处是两套算法，报告里看不出"实际跑了什么"——这正是要用 tune
实测结论替代它的理由。
